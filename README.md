# 水とでんきの救急センター - Phase1 MVP

## 目的
最小コスト・最小人員(一人・非エンジニア)で、Uber型マッチングプラットフォームの市場検証を行う。

## 唯一の正(Single Source of Truth)
すべての設計判断は `/docs` 配下のドキュメントを正とする。ChatGPT・Claude・Cursor・その他のAIツールは、作業前に必ずこの配下の最新版を参照すること。

## ドキュメント構成

| ファイル | 役割 |
|---|---|
| `docs/vision.md` | 事業の目的・MVPで検証すること・KPI・やらないこと |
| `docs/assumptions.md` | 検証すべき仮説一覧(週次で更新される) |
| `docs/data_model_phase1.md` | ドメインモデル・エンティティ設計 |
| `docs/business_workflow.md` | 顧客・加盟店・運営・例外の業務フロー |
| `docs/adr/` | 技術選定・アーキテクチャの意思決定記録(ADR) |

## 変更ルール(開発憲章)

**設計書が更新されていない状態で、Bubbleの構造(データモデル・業務フロー・技術選定)を変更しない。**

```
要件変更 → vision.md / data_model_phase1.md 更新 → 必要ならADR追加 → Bubble変更
```

### このルールの適用範囲
- **対象:** データモデルの変更、業務フローの変更、技術選定の変更(例:新しい外部サービスの導入)
- **対象外:** 文言・配色・レイアウトなど見た目だけの変更(この場合は設計書更新なしでBubbleを直接変更してよい)

このルールを厳格に保つため、対象を上記に限定する。すべての変更を対象にすると運用が形骸化するため、意図的に範囲を絞っている。

## AIの役割
AIは提案者であり、決定者ではない。最終的な意思決定は常にプロダクトオーナー(あなた)が行う。

## 開発原則

```
Business First → Data Second → UI Third
```

業務フロー(誰がいつ何を判断するか)を固めてからデータモデルを検証し、その後にBubbleの画面・Workflowを作る。この順序を逆にしない。
